### 1

**Problem.** The on/off decision is written twice. `MainActivity` disables, sends to overlay settings, or (on Android 13+) requests `POST_NOTIFICATIONS` and then enables. `BubbleTile` does the same three-way choice without the notification request.

**Why it hurts.** On API 33+, a user who grants "Sobrepor a outros apps" and from then on enables the bubble only from the tile never gets the permission prompt, so the "Toque para desligar" notification, one of the two documented ways to turn the bubble off (README), never shows. The hold gesture, the tile and the app icon still turn it off. Every new precondition for enabling has to be added in both places, and they have already drifted.

**Evidence.**
- `BubbleTile.kt:18-28`: `!enable -> BubbleService.disable(this)` / `Settings.canDrawOverlays(this) -> BubbleService.enable(this)` / `else -> { openApp(); return }`
- `MainActivity.kt:15-33`: the same branches, plus `if (Build.VERSION.SDK_INT >= 33 && checkSelfPermission(Manifest.permission.POST_NOTIFICATIONS) != ...) requestPermissions(...)`. The `SDK_INT >= 23` check at `:21` is dead code (minSdk 23, `app/build.gradle.kts:17`).
- `BubbleService.kt:161-164`: both read the process-global `var enabled`.

**Strategy.**
1. Behaviour-preserving: extract a pure `toggleAction(enabled, canOverlay): Disable | Enable | AskOverlay` (in the style of `Taps`) and use it from both callers, each keeping its own side effects. Add a JVM test.
2. Approved change (Decision 1): when the tile enables on API 33+ without the notification permission, route through `MainActivity` (`openApp()`), which already does the request. A `TileService` cannot request permissions itself.

### 2

**Problem.** `PopupActivity.onCreate` calls `begin(textFrom(intent))` unconditionally, and `started` is not saved. The only thing preventing a second translation on rotation or a light/dark switch is that each entry point's manifest block carries the full `configChanges` string. That string is pasted by hand into each `<activity>`, and nothing checks it.

**Why it hurts.** Adding another entry point (the comment anticipates "share") means copying the manifest block. If one token (such as `uiMode`) is missing, nothing fails to build, but rotating or switching theme sends the text to Google again and restarts the auto-hide timer.

**Evidence.**
- `PopupActivity.kt:35-40`: "Every entry point declared in AndroidManifest needs ... android:configChanges ... (otherwise it redoes the translation and restarts the time)"
- `PopupActivity.kt:49`: `private var started = false`. `:120`: `if (!readWithFocus) begin(textFrom(intent))`
- `AndroidManifest.xml:22,50`: the same 8-token `configChanges` string twice.

**Strategy.** Add a JVM unit test in `app/src/test` that parses `AndroidManifest.xml` and asserts that every activity with `@style/Popup` has the full `configChanges` set and `excludeFromRecents="true"`. Optionally make it hold even with a wrong manifest: save `started` and the rendered result in `onSaveInstanceState`, and skip `begin` on restore.

### 3

**Problem.** `HttpFetcher.fetch` catches every `Exception`. Anything not mapped (`SSLHandshakeException`, `SocketException("Connection reset")`, a bug-level `RuntimeException`) becomes `NetworkError.Other(e.message)` and is shown as-is. `ClipboardActivity` turns a `SecurityException` into "nothing copied". There is no `Log.` call anywhere in `app/`.

**Why it hurts.** A bug report can only say "red box with English text": no stack trace in logcat. A clipboard read blocked by Android's focus rules looks exactly like an empty clipboard, which makes the Android 10+ focus logic (`readWithFocus`) hard to debug.

**Evidence.**
- `Network.kt:16`: `else -> NetworkError.Other(e.message ?: e.javaClass.simpleName)`
- `Network.kt:37-38`: `catch (e: Exception) { throw convertException(e) }`
- `ClipboardActivity.kt:13-15`: `catch (e: SecurityException) { null }  // blocked read = nothing copied`

**Strategy.**
1. Behaviour-preserving: add `Log.w(TAG, ..., e)` in the `fetch` catch and in the `SecurityException` catch. Messages stay as they are.
2. Approved change (Decision 2): test-first in `NetworkTest`, map `SocketException`/`SSLException` to `NoConnection`. The raw detail stays for everything else.

### 4

**Problem.** `Taps` drops taps within 500 ms. A tap after that starts `ClipboardActivity` with `FLAG_ACTIVITY_NEW_TASK`, `taskAffinity=""` and no `launchMode`, while a popup may still be open for up to 15 s. Whether that reuses the open popup or opens a second one (and sends a second request) is left to platform task rules that nothing pins down.

**Why it hurts.** The one-popup rule and the README privacy line ("text is only sent ... when you tap") rest on a time threshold plus implicit platform behaviour. Changing the manifest flags or the threshold can change how many requests go out, and no test would notice. The desired rule is now decided (Decision 5), but nothing in the code expresses it.

**Evidence.**
- `BubbleService.kt:147-152`: `if (!taps.accept(SystemClock.uptimeMillis())) return  // repeated tap: a single popup` then `startActivity(Intent(this, ClipboardActivity::class.java).addFlags(Intent.FLAG_ACTIVITY_NEW_TASK))`
- `AndroidManifest.xml:48-54`: `ClipboardActivity` with `android:taskAffinity=""`, no `launchMode`
- `Config.kt:5,7`: popup lifetime and `REPEATED_TAP_MS = 500L`

**Strategy.**
1. Behaviour-preserving: check on a device what happens today (see Open questions) and write the result down next to `translateCopied`.
2. Approved change (Decision 5): `launchMode="singleTask"` on `ClipboardActivity` plus `onNewIntent` that cancels the running request and re-translates in place. Keep `Taps` for bounce only.

### 5

**Problem.** The request runs through `executor.submit { ... }`, and nobody reads the returned `Future`. `translate` catches `Exception` around `fetch` and around parsing, but `joinLines`, `translationUrl` and any `Error` (for example `StackOverflowError` from the recursive `JsonMini` on a deeply nested body, or OOM on a huge clipboard) escape. The Future then holds the error, `render` is never posted, and `showLoading` has already stopped the auto-hide timer. Separately, all popups share one thread, so a popup that is stopped but not destroyed holds it for up to the 10 s connect + 10 s read-per-chunk timeouts.

**Why it hurts.** The user is left with a popup stuck on "Traduzindo…" that never hides itself and has to be dismissed by tapping outside, and the next tap waits behind the stuck request.

**Evidence.**
- `PopupActivity.kt:135-138`: `request = Requests.executor.submit { val r = translate(text, fetcher::fetch); Handler(Looper.getMainLooper()).post { ref.get()?.render(r) } }`
- `PopupActivity.kt:187-194`: `showLoading` stops the stopwatch.
- `core/.../Translator.kt:59-68`: only `catch (e: Exception)`, around `fetch` and `extract` only.
- `Taps.kt:18-21`: `Executors.newSingleThreadExecutor()`

**Strategy.** Wrap the task body in `try { translate(...) } catch (t: Throwable) { Result.Failure(...) }` so a result is always posted. Optionally cancel the request in `onStop`. The single executor stays.

### 6

**Problem.** `onStartCommand` checks `canDrawOverlays` and then calls `showBubble()`, which does `wm.addView(v, lp)` with no guard, and returns `START_STICKY`.

**Why it hurts.** If the permission is revoked between the check and `addView`, or an OEM overlay restriction refuses the window, `addView` throws `BadTokenException`/`SecurityException`. That crashes the whole process, including an open popup. `START_STICKY` asks the system to restart the service, which can crash again the same way. The `enabled` flag and the tile are wrong until then.

**Evidence.**
- `BubbleService.kt:44-51`: `if (!Settings.canDrawOverlays(this)) { ... stopSelf(); return START_NOT_STICKY }` / `if (bubble == null) showBubble()` / `return START_STICKY`
- `BubbleService.kt:130`: `wm.addView(v, lp)`

**Strategy.** Wrap `wm.addView` in try/catch. On failure, take the existing no-permission path (stop foreground, `stopSelf()`, `START_NOT_STICKY`).

### 7

**Problem.** `HttpFetcher` creates its connection with `URL(url).openConnection() as HttpURLConnection` inside `fetch`. The two-step cancel guard, the `Http(code)` mapping and the timeouts have no seam. `NetworkTest` only covers `convertException`.

**Why it hurts.** This is the module's only concurrency code, and the code behind row 5's thread sharing: a regression in `cancel()` stalls every later popup. Today it can only be checked by hand on a device.

**Evidence.**
- `Network.kt:26-41`: `if (cancelled) throw IOException("cancelado")` ... `val c = URL(url).openConnection() as HttpURLConnection` ... `if (cancelled) throw IOException("cancelado")  // cancel() may have run before the connection was stored`
- `Network.kt:45-49`: `cancel()` → `Thread { c.disconnect() }.start()`
- `app/src/test/.../NetworkTest.kt:13-35`

**Strategy.** Add a default constructor parameter, `class HttpFetcher(private val open: (String) -> HttpURLConnection = { URL(it).openConnection() as HttpURLConnection })`, so behaviour is unchanged. Then JVM tests with a fake `HttpURLConnection` can cover cancel-before-open, cancel-between-open-and-store, 503 → `Http(503)`, and a timeout → `Timeout`. This follows the existing "IO comes in as a function" wiring (`AGENTS.md`).

### 8

**Problem.** The bubble and the popup each keep a drag/long-press state machine in local `var`s captured by a touch lambda: slop, `getLongPressTimeout()`, haptics, and `putInt("x")/putInt("y")` on UP. Their meanings are deliberately opposite (Decision 9), but the mechanism is copied.

**Why it hurts.** Tap, hold and drag are the main interaction, and none of it can be unit-tested: it needs real `MotionEvent`s, `ViewConfiguration` and a `Handler`. Every timing or slop tweak is verified by hand, twice, in two copies that are already shaped differently. The project already extracts this kind of logic into pure classes (`Taps`, `Stopwatch`), so these two are the exception.

**Evidence.**
- `BubbleService.kt:95-129`: `var x0 = 0; var y0 = 0; var rx = 0f; var ry = 0f; var dragged = false`, `postDelayed(disableOnHold, ...getLongPressTimeout())`, `putInt("x", lp.x).putInt("y", lp.y)`
- `PopupActivity.kt:220-257`: same ingredients, with the long press arming the drag, plus pausing the stopwatch and a synthetic CANCEL.

**Strategy.** Extract a pure gesture classifier in the style of `Taps`: `down(now, x, y)`, `move(now, x, y)`, `up(now)` with `slop`/`holdMs`, returning Tap / Hold / DragTo / DragEnd. Each callback then maps MotionEvents in and acts on the result with its own meaning. Start with the bubble (simpler). Moving the saved-position read and write into one small helper fits in the same pass.

### 9

**Problem.** Core claims to be "the only place" for user-facing messages and owns the network and parse-failure text. The app hard-codes the text for `TooLarge`, `NoLetters` and the empty case, plus "cancelado". The app also trims and checks for empty before calling `translate`, which checks again after `joinLines`. `cases/validation.json` checks only the result type, never the text the README promises.

**Why it hurts.** Adding a `Result` case or rewording a message means editing app and core, with no case to catch drift between them or against the PC twin. The core comment points maintainers at the wrong module. Two empty checks can disagree when normalisation changes (for example, text that is not blank before `joinLines` but is blank after it reaches core's check, not the app's).

**Evidence.**
- `PopupActivity.kt:128-131`: `val text = raw?.trim().orEmpty(); if (text.isEmpty()) { noText(NOTHING_COPIED); return }`
- `PopupActivity.kt:145-154`: `is Result.TooLarge -> show("Texto grande demais (${r.n} caracteres)", error = true)`, `Result.NoLetters -> noText("Nada para traduzir")`. `:295`: `const val NOTHING_COPIED = "Nada copiado"`
- `Network.kt:27,31`: `IOException("cancelado")  // user-facing message, kept in pt-BR`
- `core/.../Translator.kt:25`: "the only place for network error messages (user-facing, pt-BR)". `cases/validation.json`: `"expected": {"type": "no_letters"}`

**Strategy.**
1. Behaviour-preserving and contained: in app, drop the duplicate trim/empty check and let `Result.Empty` decide, keeping `noText(NOTHING_COPIED)` for the null-intent case.
2. Per Decision 3: move the Result → text mapping into core (`fun Result.message(): String?`), with the same strings. Add an expected `message` to `cases/validation.json`. This touches `pc/core.py`'s tests if they compare the whole `expected` object, which is why the blast radius is Systemic. The warn-or-close policy (Decision 4) stays in app.

### 10

**Problem.** The `release` build type sets only signing. There is no `isMinifyEnabled`, `isShrinkResources` or `proguardFiles`, and no rules file.

**Why it hurts.** Public GitHub release APKs ship unused stdlib and resources, unoptimised. Turning R8 on later means finding keep-rule breakage in a build that has never been minified.

**Evidence.** `app/build.gradle.kts:36-40`: `release { if (keystore != null) signingConfig = signingConfigs.getByName("release") }`

**Strategy.** Set `isMinifyEnabled = true`, `isShrinkResources = true` and `proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"))`, then smoke-test the release APK: bubble, popup, QS tile, selection menu. The code uses no reflection, so the risk is low. The silent unsigned local build stays (Decision 8).

## Cleanup plan

- **Phase 1, contained**: 1, 2, 3, 5, 6, 10. Do 1 and 2 first (a shipped bug, and the contract the next entry point would copy), then the three robustness guards, which are small and independent, then 10 with its smoke test.
- **Phase 2, complexity**: 7, 8, 4. The fetcher seam first, because it makes the cancel path testable before anything touches the request lifecycle. Then the gesture classifier. Then 4, after the device check in Open questions.
- **Phase 3, structure**: 9 (**Systemic**: pinning message text in `cases/` reaches the PC twin's tests, so it is not this module's to schedule alone). Its step 1 (drop the duplicate empty check) can ship with Phase 1.

**Before the next feature lands in this module** (especially a new popup entry point such as share): clear 1 and 2. A new entry point copies both the toggle and manifest patterns. Also settle 9's message ownership first, or the new entry point's text will have no clear home.
